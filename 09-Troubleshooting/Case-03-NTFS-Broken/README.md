# Case 03. Сломанные NTFS-права на папке HR



## Ситуация



Клиент **User3 (HR)** не может открыть сетевую папку `\\192.168.1.10\HR`. При попытке доступа Windows выдаёт: **«У вас нет разрешения на доступ к этому сетевому ресурсу»**.



- **Тип проблемы:** File Share / Permissions

- **Клиент:** User3 (HR)

- **Ресурс:** `\\192.168.1.10\HR` (папка `C:\Shares\HR` на сервере)



## Диагностика



### 1. Проверка членства в группе



В **ADUC** открыл свойства пользователя User3 → вкладка **«Член групп»**.



**Результат:** User3 является членом группы `HR_Users`. **Значит, проблема не в отсутствии группы у пользователя.**



### 2. Проверка Share Permissions



Свойства папки `C:\Shares\HR` → вкладка **«Доступ»** → **«Расширенная настройка»** → **«Разрешения»**.



**Результат:**

- `HR_Users` — **Change** (Изменение)

- `Администраторы` — Full



**Share-уровень настроен правильно.** Группа `HR_Users` имеет доступ.



### 3. Проверка NTFS Permissions



Свойства папки `C:\Shares\HR` → вкладка **«Безопасность»**.



**Результат:** группы `HR_Users` в списке **нет**. Остались только:

- `СОЗДАТЕЛЬ-ВЛАДЕЛЕЦ`

- `СИСТЕМА`

- `Администраторы`



**Причина найдена:** группа `HR_Users` была **удалена с NTFS-уровня**.



### 4. Почему это привело к отказу доступа



Правило: **итоговые права = пересечение Share и NTFS**.



| Уровень | Группа HR_Users | Итог |

|---|---|---|

| Share | ✅ Change | — |

| NTFS | ❌ Отсутствует | — |

| **Итог** | — | **Нет доступа** |



Хотя Share-уровень разрешал доступ, **NTFS-уровень блокировал**. В результате — доступ закрыт для **всех членов группы HR_Users**, не только для User3.



## Решение



### 1. Вернуть группу в NTFS-права



**Через GUI:**



1. Свойства папки `C:\Shares\HR` → вкладка **«Безопасность»**.

2. Кнопка **«Изменить»** → **«Добавить»**.

3. Ввести `HR_Users` → **«Проверить имена»** → **ОК**.

4. Выделить `HR_Users` → поставить галочку **«Изменение»** (Modify).

5. **ОК** → **ОК**.



**Через PowerShell:**



```powershell

icacls "C:\Shares\HR" /grant "LAB\HR_Users:(OI)(CI)M"

```



Где:

- `OI` (Object Inherit) — наследование на файлы.

- `CI` (Container Inherit) — наследование на подпапки.

- `M` (Modify) — право на изменение.



### 2. Проверка



```powershell

icacls "C:\Shares\HR"

```



Результат:

```

C:\Shares\HR LAB\HR_Users:(OI)(CI)(M)

&#x20;           BUILTIN\Администраторы:(OI)(CI)(F)

&#x20;           NT AUTHORITY\СИСТЕМА:(OI)(CI)(F)

&#x20;           СОЗДАТЕЛЬ-ВЛАДЕЛЕЦ:(OI)(CI)(IO)(F)

```



Группа `HR_Users` вернулась на NTFS-уровень.



### 3. Подтверждение с клиента



На клиенте под `LAB\User3`:

1. Проводник → `\\192.168.1.10\HR` — папка **открылась**.

2. Файл `test-hr.txt` — **доступен**.

3. Доступ восстановлен.



## Причина сбоя



**В рамках учебного кейса:** группа `HR_Users` была **вручную удалена** из NTFS-прав командой:



```powershell

icacls "C:\Shares\HR" /remove:g "LAB\HR_Users"

```



Это **имитация реальной ситуации**, когда администратор или скрипт случайно сбрасывает права на папку.



**Что бы я делал в реальной работе для поиска причины:**



1. Проверил бы **Event Viewer** на контроллере домена → журнал **Security** → **Event ID 4670** («Изменены разрешения объекта»). Там видно — **кто** и **когда** изменил права.

2. Проверил бы **историю изменений** в системе управления конфигурацией (если есть).

3. Опросил бы коллег — не менял ли кто-то права в последнее время.

4. Проверил бы, не применяется ли **GPO** с настройками безопасности на папку.

5. Проверил бы **скрипты** и **задачи планировщика**, которые могут затрагивать права на папки.



## Share vs NTFS — ключевое различие



**Share Permissions** — права **на уровне сети**. Работают только при доступе через `\\server\share`. Настраиваются во вкладке **«Доступ»**.



**NTFS Permissions** — права **на уровне файловой системы**. Работают и локально, и по сети. Настраиваются во вкладке **«Безопасность»**.



**Правило пересечения:** пользователь получит доступ **только если он разрешён на обоих уровнях**. Если хотя бы один уровень запрещает — итог = запрет.



**Практика:** Share настраивают **широко** (например, Change для всех доменных), NTFS — **узко** (только HR_Users). Итог определяет NTFS.



## Ключевые выводы



- **Диагностика проблемы доступа** идёт **по двум уровням**: сначала Share, потом NTFS.

- **Членство в группе** — проверяется первым делом: если пользователя нет в группе, остальное неважно.

- **NTFS-права** — основной механизм безопасности. Share — вспомогательный.

- **`icacls`** — быстрый способ посмотреть и изменить NTFS-права.

- **Проблема с группой** влияет на **всех её членов**, а не на одного пользователя.
